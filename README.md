# broadlistening-visualizations

広聴AI（[kouchou-ai](https://github.com/digitaldemocracy2030/kouchou-ai)）の分析結果を、散布図以外の見せ方で描く可視化の試作とカタログ。

ここで試して、使われたものだけを kouchou-ai 本体（公開ビューアの可視化 plugin）に入れるかどうか判断する。本体に入れるかを先に決めずに、まず個人 repo で作って見せる、という置き場。

- デモ：https://nishio.github.io/broadlistening-visualizations/
- 方針の経緯：[kouchou-ai-developer-wiki の open-decisions A13](https://nishio.github.io/kouchou-ai-developer-wiki/analyses/open-decisions)

## 入力：`public_result.json`

可視化はどれも、広聴AI の公開用 artifact `public_result.json`（kouchou-ai の `docs/development/public-result.md`、schema_version 1）を入力にする。

- 広聴AI で作ったどのレポートでも同じ可視化を描ける
- 本体に入れると決めたとき、同じ入力を読む plugin を書くだけで済む
- 試すために本体（公開契約やビューア）は変えない。題材の列（このデータでは PR の番号や作成日時）は変換スクリプトで `arguments[].attributes`（自由形式）に入れ、どの属性が同じ投稿を束ねるか・どれが日時かなどは URL 引数で渡す。各節の「`public_result.json` に足りない項目」は、本体に入れると決めたときに要るものの控え

## 共通の題材：チームみらい 2025 オープンデータ

[nishiohirokazu/team-mirai-2025-embeddings](https://huggingface.co/datasets/nishiohirokazu/team-mirai-2025-embeddings)（CC BY 4.0）。2025 年参院選の「しゃべれるマニフェスト」に届いた政策提案 PR 9,688 件から抽出した意見 21,348 件の広聴AI 分析結果（2 次元配置・20/400 クラスタ・表札・英訳・1536 次元埋め込み）。PR ごとの作成日時・merge の有無・作者の種別の表も入っている（作成日時は話題の流れが使う。merge の有無と作者の種別は、要約から落ちた声の属性ごとの割合に出る）。

出典：チームみらい・しゃべれるマニフェスト参加者 / データセット nishiohirokazu/team-mirai-2025-embeddings（CC BY 4.0）

## 作り方

[uv](https://docs.astral.sh/uv/) を使う。

```sh
# 1. データを取る（--embeddings で 1536 次元の埋め込みも。約 120MB）
uv run scripts/fetch_team_mirai.py --embeddings

# 2. public_result.json の形に変換（階層リスト・自分の声を探す・話題の流れは、これだけを読む）
#    意見の attributes には、PR 番号 pr_number のほか、PR の表（prs.parquet）から作成日時 created_at（UTC の ISO 8601）・
#    merge されたか merged・作者の種別 author_kind が入る（scripts/team_mirai_to_public_result.py の _pr_attributes）
uv run scripts/team_mirai_to_public_result.py --out docs/data/team-mirai-2025/public_result.json

# 3. マンダラート用の木を作る（約 30 秒）
uv run scripts/build_mandalart_tree.py docs/data/team-mirai-2025/public_result.json \
    --embeddings data/team-mirai-2025/kouchou-ai-embeddings-1536dim.parquet \
    --out docs/mandalart/team-mirai-2025.json

# 4. 付箋ズーム用の配置を作る（約 10 秒）
uv run scripts/build_sticky_layout.py docs/data/team-mirai-2025/public_result.json \
    --out docs/sticky/team-mirai-2025.layout.json

# 5. 対立軸ビュー用の軸と採点を作る（LLM を使う。下記「対立軸ビューの作り」）
uv run --group llm scripts/build_divcon.py docs/data/team-mirai-2025/public_result.json \
    --clusters 1_13,1_1,1_20,1_19 --out docs/divcon/team-mirai-2025.json
#   OpenAI ならキーを環境変数 OPENAI_API_KEY か data/.env に。OpenAI 互換の接続先なら
#   --endpoints <追跡しない JSON> --backend <名前> --model <モデル名>（並列は既定で 2）

# 6. 賛否スライダー用：まとまりごとに賛否スコアを付けた public_result.json を作り（LLM を使う）、重みごとの配置を作る
uv run --group llm scripts/add_opinion_stance.py docs/data/team-mirai-2025/public_result.json \
    --target "1_13=原子力発電を今後も活用すること" \
    --target "1_1=選択的夫婦別姓や同性婚など、家族のあり方の選択肢を法的に広げること" \
    --target "1_20=外国人・移民の受け入れを広げること" --target "1_19=女性天皇・女系天皇を認めること" \

for c in 1_13 1_1 1_20 1_19; do
  uv run --group umap scripts/build_stance_slider.py docs/data/team-mirai-2025-stance/$c/public_result.json \

done
#   （任意）賛否を無視した配置との比べ（下記「逆に、賛否を無視したら元の広聴AI になるか」）
uv run --group umap scripts/check_stance_erasure.py --embeddings data/team-mirai-2025/kouchou-ai-embeddings-1536dim.parquet \
    docs/data/team-mirai-2025-stance/{1_13,1_1,1_20,1_19}/public_result.json

# 7. 要約から落ちた声用の孤立度を作る（約 15 秒。下記「要約から落ちた声の作り」）
uv run scripts/build_rare_voices.py docs/data/team-mirai-2025/public_result.json \

    --group-by pr_number \

# 9. （任意）「自分の声を探す」の近さの目安と文字の組の選び方を確かめ直す（LLM は使わない。約 30 秒。

# 10. 見る
cd docs && python3 -m http.server 8000
# -> http://localhost:8000/  （mandalart/ ・ sticky/ ・ divcon/ ・ slider/ ・ tree/ ・ find/ ・ rare/ ・ links/ ・ timeline/）
#    束ねる属性・タイムゾーン・印などは URL で渡す（カタログのリンクと同じ）。例：
#    http://localhost:8000/find/?group=pr_number
#    http://localhost:8000/timeline/?group=pr_number&tz=Asia/Tokyo&marks=2025-07-03:公示,2025-07-20:投票日
```

広聴AI で作った自分のレポートで描くときは、出力ディレクトリの `public_result.json` を使う。

- 階層リストは `?data=<public_result.json の URL>` でそのまま読める。付箋ズームは 4 に渡して配置を作り、`?data=<public_result.json の URL>&layout=<配置の json>` で読む
- マンダラートは 3 に渡して木を作り、`?data=<木の json>` で読む（`--embeddings` を省くと 2 次元配置で割る）
- 「自分の声を探す」も `?data=<public_result.json の URL>` でそのまま読める。`?group=<属性>` で「同じ投稿」として束ねる属性を選ぶ（トップレベルの項目か `attributes` の名前。省略時は `comment_id`、チームみらいのデータでは `pr_number`）。`#q=<文>` か `#post=<URL か値>` を付けると、開いたときにその文で探す・その投稿を引く。近さの目安はチームみらい 2025 のデータで決めた固定値なので、別のレポートでは合わないことがある（9 の `build_find_check.py` にそのレポートを渡すと確かめ直せる）
- 要約から落ちた声は、7 で孤立度を作り、`?data=<public_result.json の URL>&rare=<孤立度の json>` で読む（`--group-by` を省くと comment_id で束ねる。`--embeddings` を省くと x / y の距離で測るが、下記のとおり似た意見の少なさとは別のものを測ってしまう）
- 一緒に言われた話題は、8 で組を作り、`?data=<public_result.json の URL>&links=<組の json>` で読む（組の json が別のレポートのものなら、そう表示して止まる）
- 話題の流れも `?data=<public_result.json の URL>` でそのまま読める。日時の属性は `?time=<属性名>`（省略時は ISO 8601 として読める属性を探す）、日付を区切るタイムゾーンは `?tz=<IANA 名>`（省略時はブラウザの地方時）、同じ投稿を束ねる属性は `?group=<属性名>`（省略時は `comment_id`）で渡す

## 意見マンダラートの作り

- 広聴AI の既定の階層づくり（最細の段を k-means で切り、Ward で上へ併合する）では、親 1 つあたりの子の数が揃わない（このデータでは上位 20 クラスタの子の数が 1〜38）。マンダラートは中心＋8 マスなので、上から順に k-means（k=8）で割り、子が 8 以下になった節は意見そのものをマスに並べる。深さは枝ごとに違う（このデータで 5,848 節・最大 7 段）
- 埋め込みは長さ 1 に正規化してから割る（cosine）。乱数の種は 42
- 表札は LLM を使わず、各まとまりの中心に最も近い意見をそのまま使う。上の段ほど「〜が不足している」のような一般的な文になりやすいので、上の数段だけ LLM で表札を付ける余地がある
- マスの文字は、全文が収まる最大の大きさにする（10〜40px、ただし 1 行に 3 文字は入る大きさまで）。全マスを同じ歩みで二分探索するので、1 歩ごとの配置計算は 1 回ですむ。10px でも入らないマスだけ入る行数で「…」にする。画面の大きさが変わったら測り直す
  - 確かめた値（2026-11-08、Chromium）：幅 1280px で 3×3 は 26〜38px（中央値 31px）、9×9 は 13〜24px（中央値 18px）でどのマスも全文が入る。英語の 9×9 は 10〜24px で 81 マス中 4 マスが「…」。幅 390px では 3×3 が 12.5〜19px で全文、9×9 は 10px で 81 マス中 54 マスが「…」
  - 9×9 の盤は最小幅 620px で、狭い画面では横にスクロールする（以前は幅 390px でマスどうしが重なっていた）

## 付箋ズームの作り

最初の版は、画面を付箋 1 枚ぶんの升目に区切って升目ごとに 1 枚を毎フレーム選び直していたため、拡大すると付箋が入れ替わって震えた。今の版は地図アプリの地名ラベルと同じ考え方で、表示する前に全部決めておく。

- 付箋は画面上で一定の大きさ（拡大しても文字が読める）。位置は世界座標で固定
- 位置は、オリジナル（`canvas_kozaneba_prototype`）と同じく格子に寄せ、同じマスが埋まっていたら螺旋状に一番近い空きマスへずらす。こうすると最も寄った状態で全意見が重ならずに並ぶ（平均のずれは 0.76 マス）
- 拡大率を 2 倍ごとに 8 段に区切り、引いた側から順に、優先度の高い意見から「既に出ている付箋と重ならないなら出す」を決める。一度出た付箋は、寄った段でも必ず出ている（寄るほど付箋どうしの間隔は広がるので）
- 優先度：上位クラスタの代表（中心に最も近い意見の位置に、上位の表札を出す）→ 下位クラスタの代表（同じく下位の表札）→ 残りを下位クラスタごとに中心に近い順で、全クラスタを順に回す
- 表示側は意見ごとの「出始める拡大率」と今の拡大率を比べるだけ。出ていない意見は点で描く。出始めは 1.5 段ぶんかけて濃くする
- 付箋の文字は、全文が収まる最大の大きさにする（10〜28px）。付箋の大きさは一定なので、大きさと改行位置は付箋ごとに 1 回だけ決めて使い回す（寄っても文字は変わらない）。文字幅は 1 文字ずつ 1 回だけ測って大きさに比例させるので、大きさを何度試しても重くならない。句読点・閉じ括弧は行頭に置かない
- まとまりの代表の付箋は表札だけを、濃い色・太字で書く。代表の意見の本文は押すと「このまとまりの代表の意見」として出る。以前は表札と本文を 1 枚に入れていて、140×76px では両方の全文を入れると 10〜12px にしかならなかった
  - 確かめた値（2026-11-08、Chromium、幅 1280px で 3 段寄った状態の 134 枚）：表札の付箋 44 枚は 13〜18px、意見の付箋 90 枚は 10〜21px（大半が 13〜17px）。10px でも入らず「…」になったのは 1 枚

このデータでは、全体が 1000px に収まる拡大率で 27 枚、2 倍で 75 枚、4 倍で 228 枚、8 倍で 601 枚、16 倍で 2,058 枚が付箋になり、約 60 倍で全 21,348 件が付箋になる。

## 対立軸ビューの作り

元は tokoroten の [DivCon](https://github.com/tokoroten/divcon)（MIT、`experiments/divcon_analysis.py`）。同じトピックに賛否が混ざると「何が対立しているか」が見えない、という問題意識から、LLM で対立軸を見つけて各意見を軸の上に置く。kouchou-ai の docs の関連研究ページ（PR #1174）で「本体に収録していない手法」として紹介しているもの。

- 段の構成とプロンプトは DivCon のまま：3a 対立軸の発見（まとまりごとに 2〜4 本、強度 1〜5）→ 3b アンカーの生成（左極・右極の極端な主張を 10 個ずつ。実在の意見ではない）→ 4 採点（アンカーを基準に 1〜6。中立はなく、軸に当たらなければ「該当なし」）→ 5 合意可能性（合意できそうな点・根本的に対立する点）
- 変えた点

### `public_result.json` に足りない項目（公開契約に足す提案）

この可視化は、`public_result.json` と、それから作った `docs/divcon/team-mirai-2025.json`（軸・アンカー・採点・合意可能性）を読む。本体に入れるなら、次の形で `public_result.json` に載せることを提案する（どちらも省略可能なキーの追加なので schema_version は上げずに済む）。

- 意見ごとの採点：`arguments[].attributes` に数値で入れる（例 `"axis:1_13_A1": 2`）。`attributes` は契約の対象外（自由形式）なので、契約の変更は要らない。意見の分類ラベル・賛否スコア（`opinion_stance`）と同じ「意見ごとに属性を足す」形

## 賛否スライダーの作り

元は tokoroten の「センチメント次元の付与（sentiment-weighted UMAP）」（[デモ](https://sentiment-weighted-umap-animation.netlify.app/combined_interactive.html)・[コード](https://sentiment-weighted-umap-animation.netlify.app/posinega_separation.zip)）。書籍『ブロードリスニング』13.4.3 の「賛否分離」の 1 つ目のアプローチで、kouchou-ai の docs の関連研究ページ（PR #1174）でも紹介している。

- **賛否スコア**（`scripts/add_opinion_stance.py`）：広聴AI 本体の任意ステップ `opinion_stance` と同じ形にした。プロンプトは本体の既定（main `ddd0bacd` の `STANCE_PROMPT`）をそのまま使う。本体は AGPL-3.0 でこの repo は MIT なので、文は写さず、`--kouchou-ai` に渡した checkout（か、入っている `analysis_core`）から実行時に読む。意見 1 件ごとに「対象」と「意見」を渡し、-1.0〜+1.0 を `arguments[].attributes.stance_score` に入れ、判定不能には属性を付けない
  - 元の tokoroten の版は、対象のない「肯定的か否定的か」を見ていた。このデータの意見はほとんどが「〜が不足している」型で、どれも否定的な調子になるので、本体と同じく対象への賛否にした
  - 対象は 1 つのレポートに 1 つなので、まとまりごとに `public_result.json` の部分集合を作り、`config.question` を対象に置き換えた（`docs/data/team-mirai-2025-stance/<クラスタ>/public_result.json`）。対象の文はこちらで決めた：
    - エネルギー＝「原子力発電を今後も活用すること」
    - 家族＝「選択的夫婦別姓や同性婚など、家族のあり方の選択肢を法的に広げること」
    - 移民＝「外国人・移民の受け入れを広げること」
    - 皇位継承＝「女性天皇・女系天皇を認めること」
- **重みごとの配置**（`scripts/build_stance_slider.py`）：埋め込み（1536 次元、長さ 1 に正規化）の末尾に w·stance_score を足し（判定不能は 0）、cosine で UMAP。w は 0〜1.5 を 0.05 刻み（元と同じ）
  - 前の重みの座標を初期値に、50 エポックで学習し直すのは元と同じ。ただし元の学習率 1.0 のままだと、重みを変えずに学習し直しただけで点が配置の幅の 12%（中央値）も漂った
  - 学習率を 0.1 に下げ、各段を前の段に縮尺・回転・平行移動だけで重ねる（Procrustes）と、漂いは 2.5% になった。代わりに点が動ける距離も短くなる。重み 1.5 での賛否の分かれは、移民で 0.77 → 0.72、家族で 0.37 → 0.14
  - `--embeddings` を省くと、`public_result.json` の 2 次元配置 x/y を土台にする
- 重みごとに 2 つの数値を残す。本体 docs が weight の採用判断に挙げている「賛否で分かれたか」と「トピックの近さが壊れていないか」を同時に見るためのもの
  - 賛否の分かれ：賛成（> 0.2）と反対（< -0.2）を 2 群とした、2 次元でのシルエット係数
  - 話題の近さの残り：重み 0 の埋め込みで近い 15 件のうち、2 次元でも近い 15 件に入っている割合
- 表示側は重みの段のあいだを線形補間するだけ

### 逆に、賛否を無視したら元の広聴AI になるか

- 重み 0 が元の広聴AI と同じ考え方（埋め込みをそのまま UMAP にかけた配置）。ただしスライダーの重み 0 はまとまりだけで UMAP をかけ直したもので、レポートの散布図そのものではない
- 重みを負にしても無視にはならない。足すのは 1 次元だけなので、距離は |w| で決まり、正と同じだけ分かれる
- 本当に無視するには、埋め込みから賛否と相関する方向を取り除く（線形の概念消去）。`scripts/check_stance_erasure.py` で試した（2026-11-08、LLM は呼ばない。約 50 秒）

| まとまり | 埋め込みから賛否を当てる AUC：元 → 平均の差を 1 方向取り除く → ロジスティック回帰の方向を 10 回取り除く | 賛否の分かれ：元の配置 → 消去後の配置 | 話題の近さの残り：元 → 消去後 | 元の配置との近傍の重なり（seed だけ変えた配置） |
|---|---|---|---|---|
| エネルギー | 0.89 → 0.79 → 0.81 | 0.09 → 0.01 | 0.43 → 0.35 | 0.38（0.64） |
| 家族 | 0.88 → 0.70 → 0.74 | -0.01 → 0.05 | 0.51 → 0.44 | 0.52（0.76） |
| 移民 | 0.93 → 0.83 → 0.82 | 0.01 → 0.04 | 0.51 → 0.43 | 0.52（0.80） |
| 皇位継承 | 0.81 → 0.81 → 0.79 | 0.27 → 0.02 | 0.68 → 0.52 | 0.56（0.86） |

- 埋め込みには賛否がはっきり入っている（AUC 0.81〜0.93）。それでも元の配置は、皇位継承以外ではほぼ賛否で分かれていない（シルエット係数 -0.01〜0.09）。近い意見は話題で決まり、賛否の違いは 2 次元に落とすと埋もれる。このデータでは、元の広聴AI の配置がすでに「賛否をほぼ無視した地図」になっている
- 皇位継承だけは元の配置でも少し分かれていて（0.27）、取り除くと 0.02 になる
- 線形に取り除いても、賛否は消えきらない。10 方向取り除いても AUC は 0.7〜0.8 に残る。賛否は少数の方向に収まらず、話題と絡んでいる（皇位継承は 29 件しかなく、AUC の振れが大きい）
  - AUC は、取り除く方向を決める意見・分類器を学習する意見・評価する意見を分けて測った。最初に同じ意見で決めて測ったときは、消去後の AUC が 0.02〜0.08 と出た。逆向きに当てられる状態を作っていただけの見かけだった
  - 平均の差の方向は 1 回取り除くと、次の差がほぼ 0 になる。そのため 3 方向・10 方向でも値が変わらない
- 取り除いた埋め込みでかけ直した配置は、元の配置と、seed を変えたとき以上に変わる。話題の近さの残りも 0.07〜0.16 下がる。賛否と一緒に話題の情報も削れるため。賛否を無視した地図は、元の地図に戻るのではなく、話題の近さを少し失った別の地図になる
- なので、スライダーの左に「無視」の端を足しても、得るものはほぼない。足す意味があるのは、皇位継承のように元の配置がもともと賛否を拾っているまとまりだけ

### `public_result.json` に足りない項目（賛否スコア）

- 賛否スコア自体は `arguments[].attributes.stance_score` に入る（本体の `opinion_stance` がすでにそうしている）。契約の変更は要らない
- **賛否の対象が `public_result.json` に無い**。本体の `opinion_stance.target` は省略時に `question` を使うが、`target` を指定した場合、その文は `opinion_stance_summary.json` にしか残らず、公開用の契約に入らない。スコアを読む側は「何への賛否か」を知る必要がある。そこで省略可能なキーを足すことを提案する。`config.opinion_stance_target` を足すか、ほかの可視化でも要る属性ごとの説明の置き場 `attribute_meta`（下記「属性の型と役割」）に `stance_score` の対象として書く。ここでは部分集合の `config.question` を対象に置き換えて済ませた

## 「自分の声を探す」の作り

参加者が「自分が書いたことはどこにあるか、似たことを言った人はどれだけいるか」を確かめるためのページ（tokoroten の farbrain にある「自分の投稿のハイライト」と、「自分がどのクラスタにいるかわかる」という要件から）。文を入れると字面の近い意見を探し、似た声の数・どのまとまりに多いか・地図の上のおおよその位置を出す。投稿の URL か番号を入れると、その投稿から取り出された意見を地図で光らせる。

- **事前計算はしない**。ページが `public_result.json` を読み、ブラウザの中で索引を作る。入れた文はどこにも送らない（ページにもそう書いた）
- 近さは TF-IDF の cosine（0〜1）。重みは (1 + ln tf)·ln(N / df) を長さ 1 にしたもの。問いの文字の組のうち、どの意見にも無いものは df = 1 とみなして問いの長さに入れる（無視すると、データに無い話題の文が高い近さになる。「宇宙人と交信したい」が 0.28 → 0.38）
- 日本語は **2 文字の組と、ひらがな以外の 1 文字**（NFKC で正規化し、文字と数字の続きの中だけで組を作る）。英語は訳文（`translations.en.arguments`）を対象に、よく使う語（128 語）を除いた**単語と、単語の前後に空白を付けた 3 文字の組**
  - 選び方：意見 2,000 件を問いにし（同じ PR の意見は除く）、近い 10 件が広聴AI の同じまとまりに入る割合と、埋め込み（1536 次元）の近い 10 件との重なりで比べた（`scripts/build_find_check.py`）。2 文字を中心に 3 文字を足すと下がり、1 文字を足すと上がった。漢字 1 字でも話題を拾える（「原発」と「原子力発電」が「原」「発」で重なる）ため。ひらがな 1 字はほぼ助詞・語尾なので外した

| 言語 | 文字の組 | 種類 | 近い 10 件が同じ下位のまとまり | 同じ上位のまとまり | 埋め込みの近い 10 件との重なり |
|---|---|---|---|---|---|
| 参考 | 埋め込み（1536 次元の cosine） | | 0.529 | 0.810 | 1 |
| 日本語 | 2 文字 | 27,428 | 0.269 | 0.462 | 0.270 |
| 日本語 | 2・3 文字 | 111,329 | 0.239 | 0.426 | 0.239 |
| 日本語 | 1・2 文字（1 文字はすべて） | 29,075 | 0.299 | 0.508 | 0.315 |
| 日本語 | **1・2 文字（1 文字はひらがな以外）** | 29,008 | **0.303** | **0.514** | **0.320** |
| 英語 | 単語（よく使う語を除く） | 6,887 | 0.275 | 0.491 | 0.247 |
| 英語 | 3 文字（すべての単語） | 3,955 | 0.301 | 0.523 | 0.285 |
| 英語 | **単語＋3 文字（よく使う語を除く）** | 10,828 | **0.308** | **0.535** | **0.288** |

- 問いの文末の「〜してほしい」「ください」「です」「ます」「と思う」は外して比べる。意見の文はほとんどが「〜である」「〜が不足している」の形で、「ほしい」「です」という字面は 21,348 件のどれにも無い（「ます」も 1 件だけ）。外すと、例文のいちばん近い意見の近さが上がる（夫婦別姓 0.33 → 0.41、保育士 0.28 → 0.35、AI 0.28 → 0.38、同性婚 0.36 → 0.50）。データに無い話題の文は、「ゾンビ対策をしてほしい」（0.27 → 0.35。「ゾンビ企業」と重なる）のほかは変わらないか 0.01 上がるだけ
- 一致した字面は一覧で黄色の印を付ける（なぜ近いかが見える）。1 文字だけの一致に印を付けるのは漢字のときだけ（「原子力発電」の「原」「発」など。「ー」やカタカナ・英字 1 字の一致はどの文にもあり、印がちらばるだけなので）
- 要約の見出しは、近い意見が最も多い上位のまとまりが 1 つに決まるときだけ、その名前を出す（近い意見の半分以上なら「主に」、半分未満なら「最も多いのは」）。最も多いのが同数なら「k つのまとまりに分かれる」とする。下位のまとまりも、最も多いものが 1 つに決まるときだけ「中でも」を付ける（AI の例は上位のまとまりの 3 件が下位の 3 つに 1 件ずつなので付けない）
- 例文は、読んだレポートで近い意見（0.30 以上）が見つかるものだけを出す。3 つに満たないとき（`?data=` で別のレポートを読んだとき）は、大きい上位のまとまりから順に、その中の大きい下位のまとまりの表札で 5 つまで補う（表札も近い意見が見つかるものだけ）。賛否スライダー用の部分集合 `docs/data/team-mirai-2025-stance/1_1/public_result.json`（家族のまとまりの意見 659 件）で開くと、例文は 1 つだけ残り、表札 4 つで補われた

### 近さの目安と根拠

### 地図と、入れた文の位置の印

- 広聴AI の 2 次元配置（`arguments[].x / y`）に全意見を灰色の点で描き、近い意見を青の 2 段（近い・とても近い）で重ねる。近い意見が最も多い上位のまとまり（同数ならそのすべて）の点は濃い灰色にし、表札を出す（表札は光らせる点にかからない位置を上下から選ぶ）。何も探していないときは、上位のまとまりの表札を重ならない分だけ薄く出す
- 投稿で引いたときは、投稿の意見があるまとまりをすべて濃くし、投稿の意見の多いまとまりから順に表札を置く。光らせる点にかからない位置が無い表札は、最初の 1 つのほかは出さない（点は表札の上に描くので、かけると字が点に隠れて読めない。どのまとまりかは一覧に出ている）。PR #1206 では 11 のまとまりのうち、幅 1280px で 10、390px で 8 の表札が出る
- 色は配色の検証スクリプトで確かめた：青の 2 段（ライト #5598e7 / #1c5cab、ダーク #3987e5 / #9ec5f4）は、順序の段（明るさが順に並び、隣の段と見分けられるだけの差があり、薄い方の段も地の色から見分けられる）としてライト・ダークとも合格。青の 2 段と「投稿で引く」のオレンジは、どの 2 色の組でも、色覚の型を模したときの差（OKLab の ΔE×100）が 19 以上（いちばん近いのは青の 2 段どうし）
- 印は、近い意見（近い順に 20 件まで）の位置を近さで重み付けした**幾何中央値**（Weiszfeld 法 50 回）。最初に試した単純な重み付き重心は、近い意見の一部が別のまとまりにあると、意見のない所に出た。印から最も近い「近い意見」までの距離（2 次元配置の対角線に対する割合）は、重み付き重心だと介護職員 6.9%・外国人 6.0%・ガソリン税 3.6%・AI 3.3%、幾何中央値だと例文 18 個（近い意見のあるもの）すべてで 0.4% 以内
- 「近い意見のあたりに寄る」で近い意見を囲む範囲に寄る（幅 1280px の画面、原発の例で 8.2 倍）。点に乗せると意見、押すと出典と「この意見で似た声を探す」が地図に重ねて出る。一覧の行に乗せる・押すと地図の点に輪が付く

### 投稿で引く

- 投稿の URL（`arguments[].url`）か、束ねる属性の値で引く。束ねる属性は `?group=`（省略時は `comment_id`。カタログからは `?group=pr_number`）。可視化の側に `pr_number` とは書いていない。URL は末尾に `/files`・`?…`・`#…` が付いていても当たる。`?group=` に無い属性を渡すと `comment_id` で束ねた旨を出す
- 引いた投稿の意見ごとに、まとまりと「似た声 N 件（この投稿を除く）」を出し、「この意見で似た声を探す」で文の検索に移る（同じ投稿の意見は除いて数える）
- 確かめた値（2026-11-11）：`?group=pr_number` で「3721」→ 2 件、同じ PR の URL に `/files?diff=split#top` を付けても 2 件、「#1206」→ 18 件、「99999」→ 見つからない旨と入れ方の例。`?group` を省くと「csv-1」→ 1 件（PR #3721 の 1 つ目の課題）、PR #3721 の URL → 2 件。PR #3721 の「発達障害を持つ子どもへの合理的配慮が不十分である」から探すと、似た声 23 件（同じ PR の 2 件を除く）
- 「似た声」の件数の横に、束ねる属性で数えた件数も出す（マイナンバーの例で意見 77 件・pr_number 59 件）。どちらも人数ではない（1 人が複数の PR を出しうる。`public_result.json` に人を表す項目は無い）

### 字面の近さでできないこと

- 言い換えは拾えない。「給料」はデータに 1 件も無く（意見は「給与」で 20 件）、「保育士の給料を上げてほしい」は「保育士」の字面で当たっている。「がん検診を無料にしてほしい」は近い意見なし（いちばん近いもので 0.16）
- 賛否を区別しない。「原発の再稼働に反対です」の近い 11 件には、「原子力発電の再稼働に関する手続きの迅速化が求められている」（0.43）のような進める側の意見も同じくらい近く出る。「反対」という字面は 21,348 件中 9 件にしかない
- ありふれた字面は重みが小さい。「AI」は 1,359 件にあり、「AI で行政を効率化してほしい」は「効率化」の字面で当たる
- 意味の近さで探すには、入れた文を埋め込み（今の埋め込みと同じモデル）にする API が要り、ブラウザだけではできない（入れた文をその API に送ることになる）。任意入力の埋め込みは、このページでは使っていない（使ったのは上の比べだけ）。字面の近い 10 件と埋め込みの近い 10 件の重なりは、意見どうしで 32%

### `public_result.json` に足りない項目（自分の声を探す）

- なし。使っているのは `arguments[]` の `arg_id` / `argument` / `comment_id` / `x` / `y` / `cluster_ids` / `url` / `attributes`（`?group=` の属性と、投稿で引いたときの表示）、`clusters[]` の `id` / `level` / `label` / `takeaway` / `value`、`translations.en` の `clusters` と `arguments`、`config.enable_source_link`

## 要約から落ちた声の作り

表札と要約は、まとまりの多数派を代表する。その反対側の、似た意見がほとんど無い声を、まとまりごとに候補として並べる。重要かどうかは決めない。

- **孤立度**（`scripts/build_rare_voices.py`）：同じ投稿の意見を除いて、10 番目に近い意見との近さ。埋め込みを長さ 1 に正規化した cosine 類似度で、低いほど孤立している
  - 同じ投稿を除くのは、1 つの投稿から取り出した意見どうしを「似た意見がある」と数えないため。束ねる属性は `--group-by`（既定は comment_id）。このデータでは 1 本の PR が複数の comment_id に分かれているので、`--group-by pr_number` で PR ごとに束ねた（8,909 本、1 本あたり 1〜18 件）
  - 1 番目でなく 10 番目（`--k`）にするのは、似た意見が 1 件あるだけで孤立していないことにしないため
- **孤立した声**：孤立度の低い方から全体の 5%（`--percent`）。上位・下位のまとまりごとと、属性のうち値が 2〜8 通りのもの（このデータでは merged と author_kind）の値ごとに、その割合を出す
- 意見ごとに、いちばん近い「他の投稿の」意見とその近さも残す。表示ではこれを薄く添え、本当に孤立しているか（言い回しが違うだけではないか）を読み手が確かめられるようにした
- 生成物（`docs/rare/team-mirai-2025.json`、約 59KB）には、孤立した声の arg_id・順位・近さと、まとまり・属性ごとの件数だけを書く。本文・表札・英訳は、表示側が `public_result.json` から arg_id で引く。付箋ズームと同じく `?data=` に `public_result.json`、`?rare=` に生成物を渡す。arg_id が見つからない組み合わせは、その旨を出して描かない
- 表示
  - 上の棒は 1 色（明 `#2a78d6`・暗 `#3987e5`。どちらも面に対して 3:1 以上）の横棒で、縦の細線が全体の 5%。値は行ごとに文字で出すので、行の並びがそのまま表になる。上位 20・下位 400・属性を切り替えられ、行を押すとその声だけに絞る。下位のまとまりで絞ると、そのまとまりの表札と要約も出す
  - 棒の表札は 2 行まで折り返す。幅 600px 以下では、表札を棒の上の行に全幅で出す（棒の横の細い列に入れていたときは、幅 390px で上位 20 のうち 18 の表札が「…」で切れていた）
  - 一覧は、上位のまとまりごと（表札と要約は畳める。並びは棒と同じく割合の高い順）と、全まとまり通しの 2 つ。各声に、近さ・順位・入っている下位のまとまりの表札、いちばん近い他の投稿の意見、同じ投稿のほかの意見（押すと出る）を添える
  - 同じ投稿の意見は `?group=` の属性で束ねる。省くと生成物を作ったときの `--group-by`（無ければ comment_id）。孤立度は事前計算なので、`?group=` で変わるのはこの表示だけ
  - レポートが元のコメントを公開していれば（`comments`）、各声から「元のコメント」を開ける。このデータでは `comments` が空なので出ない
  - 読み込むまでは「読み込み中…」だけを出す。生成物が `public_result.json` と合わないときや読めないときは、その旨だけを出し、検索などの操作の行も出さない
- `--embeddings` を省くと、`public_result.json` の x / y の距離で測る。ただし下のとおり、似た意見の少なさとは別のものを測ってしまう

### `public_result.json` に足りない項目（要約から落ちた声）

- **埋め込み**：`public_result.json` に無い。任意の追加入力（`--embeddings`）にし、無ければ x / y で測る道を残したが、上のとおり x / y では似た意見の少なさを測れない（重なり 12%）。本体に入れるなら、孤立度は「意見ごとのスコア」なので `arguments[].attributes` に入れれば契約の変更は要らない（例：10 番目の近さ `rare_k10` と、いちばん近い他の投稿の意見の arg_id）。何を測った値か（k・束ねた属性・空間）は、下記「属性の型と役割」の `attribute_meta` に書ける
- **「同じ投稿」を表す属性**：どの属性が同じ人・同じ投稿を表すかを書く場所が、契約に無い。本体のレポートでは comment_id が入力の 1 件なので既定の comment_id で足りるが、この題材では comment_id が「PR の中の課題 1 件」なので、`pr_number` を引数で渡した。下記「属性の型と役割」の `role: "group"` で書ける
- **元のコメント本文**（題材の事情）：このデータでは `comments` が空なので、抽出で文脈が落ちた断片を元の提案文で読み直せない。同じ投稿のほかの意見で代えた。契約には `comments` があり、元のコメントを公開しているレポートなら、そのまま各声から開ける

## 一緒に言われた話題の作り

散布図は「文が似ているか」で意見を置く。こちらは「同じ投稿の中で一緒に書かれたか」で下位クラスタどうしを線で結ぶ。地図の上で離れているのに一緒に書かれる組は、散布図の裂け目（同じ話題が地図の上で離して置かれた所）の候補になる（文も遠ければ、別の話題を一緒に書いているだけかもしれない。下の「文の近さ」）。kouchou-ai-developer-wiki の「クラスタ内 MST ＋クラスタ間の橋」（[graph-visualization-proposal-2026-05-25](https://nishio.github.io/kouchou-ai-developer-wiki/analyses/graph-visualization-proposal-2026-05-25)、nishio 発案）の橋を、LLM ではなく実データの共起で引く版でもある。地図は作り直さず、広聴AI の x / y の上に線を重ねる（wiki の移植経路でいう A）。

- **束ねる単位**：既定は `comment_id`。`--group-by <属性名>` を渡すと `arguments[].attributes` のその属性で束ねる。このデータは変換で 1 本の PR を課題ごとの comment に割っているので（comment 18,802・意見のある PR 8,909）、`pr_number` で束ねた
  - PR で束ねると、8,909 本の 41%（3,666 本）が 2 つ以上の上位クラスタに、63%（5,589 本）が 2 つ以上の下位クラスタにまたがる。comment_id では 18,802 件のうち 1,005 件・1,659 件だけ
- **偶然の見込み**：組 (x, y) ごとに、両方を含む投稿の数 k と、偶然なら見込まれる数 λ を出し、ポアソン分布の P(X ≥ k) を p 値にする。補正は全 79,800 組（下位 400 の組）で行う
  - λ は層別にした。含む下位クラスタの数 s が同じ投稿どうしで n_x^s · n_y^s · (s−1) / (s · N_s) を出し（n_x^s は x を含む投稿の数、N_s は投稿の数）、s について足す。話題が 1 つだけの投稿は組を作れず、話題の多い長い投稿ほど組を作りやすいことを織り込むため
  - 最初は λ = n_x · n_y / N（N は投稿の数）で数えた。これは話題が 1 つだけの投稿も組を作れるものとして数えるので、全組の λ の合計が実際の共起の合計の 1.16 倍になる（層別は 0.994）。comment_id で束ねると 6.6 倍になり、1 組も残らない。PR で束ねたときの厳しい段は、どちらでも 127 組で、うち 104 組が共通
  - 層別にすると厳しい段から落ちる 23 組は、長い投稿によく出る話題どうしの組（例：教育の下位クラスタどうし。x を含む投稿・y を含む投稿の話題の数の平均が 3.2、全まとまりでは 2.7）。代わりに入る 23 組は、短い投稿で一緒に書かれる組（エネルギー・家族など、同じく 2.3）
- **厳しい段と緩い段**：厳しい段は Bonferroni（全体で 1%）、緩い段は Benjamini–Hochberg（偽発見率 5%）。どちらも、一緒に書かれた投稿が 3 本に満たない組は引かない（2 本だけなら同じ人の 2 回の投稿でも起きる。緩い段で 3 組が当たった）
- **地図上の距離**：下位クラスタの重心（意見の x / y の平均）どうしの距離を、全意見の外接矩形の対角線で割ったもの。10% 以上を「離れた組」とする
- **文の近さ（任意）**：`--embeddings` を渡すと、下位クラスタの埋め込み（1536 次元、長さ 1 に正規化）の重心どうしの cosine で全 79,800 組を近い順に並べ、組ごとに上から何割目かを付ける。地図で離れていても文が近ければ散布図の裂け目、文も遠ければ別の話題を一緒に書いている、と見分けるため。省いても組は同じで、ページはその一文を出さない
- **根拠**：組ごとに、両方を含む投稿ごとの「x 側の意見 id と y 側の意見 id」を持つ（生成物は 207 KB）。文・英訳・出典の URL は、ページが `public_result.json` から引く
- **表示**：意見を灰色の点、下位クラスタの重心を小さな丸で置き、組を線で結ぶ。太さは一緒に書かれた投稿の数、離れた組は橙、近い組は灰。線を押すと右（スマホでは下）の欄に根拠の投稿を左右 2 列で並べ、地図では両側のまとまりの意見を青と緑みの青で塗り、根拠の意見どうしを細い線で結ぶ（寄ると見える）。重心を押すとその相手の一覧。右の欄の一覧（地図上の距離・投稿の数・偶然の何倍か で並べ替え）は表としても読め、キーボードでも選べる。`#p=<x>,<y>`・`#c=<まとまり>` で選んだ状態から開ける
  - 20 ある上位クラスタは色分けせず、地図の上に名前を出す（20 色は見分けられない）。色は灰・橙・青・緑みの青だけにし、橙・青・緑みの青は色覚の模擬（1 型・2 型・3 型）でも全組で見分けられることを確かめた（ライト・ダークとも。色差 ΔE76 は最小 16）。ライトの地の色に対して橙（2.9:1）と緑みの青（2.6:1）はコントラストが 3:1 に届かないので、名前と一覧を必ず併せて出す
  - 描画 1 回（ヘッドレス Chromium・GPU なし、ラスタ化まで）は、全体表示で厳しい段 28ms・緩い段 29ms。うち 23ms は意見 21,348 点の塗りで、線は数 ms（色と太さが同じ線は 1 つの path にまとめて描く）。8 倍に寄ると 7ms

### `public_result.json` に足りない項目（一緒に言われた話題）

- `comment_id` で束ねるなら、契約の中だけで描ける（`x` / `y`・`cluster_ids`・表札・英訳・`url`）。上の表のとおり、層別の見込みなら comment_id 単位でも線が引ける
- このデータは 1 本の PR を課題ごとの comment に割っているので、`attributes.pr_number` で束ねた。`attributes` は自由形式なので契約は変えずに済む。ただ、どの属性が「同じ投稿（同じ人）」を表すかを契約から知る手段がなく、いまは `--group-by` で人が指定している。下記「属性の型と役割」の `attribute_meta` に「投稿の単位」という役割（`role: "group"`）を持たせれば、ビューアが自分で束ね方を選べる
- 元の投稿の本文（`comments`）がこのデータでは空なので、根拠には抽出後の意見しか出せない。契約にはすでに `comments`（`enable_original_comments`）があるので、元の投稿を公開してよいレポートなら並べられる

## 話題の流れの作り

ほかの可視化は「いつ届いたか」を描かない。日時の属性を持つレポートで、どの話題がいつ増え・減ったかを見せ、期間を選ぶとその期間の意見まで降りられるようにした。

- 入力は `public_result.json` だけで、事前計算はしない。headless Chromium で測ると、意見 2 万件の振り分けは約 140〜170ms、期間を変えたときの比べは 1 回 1ms 前後、比べた結果の描き直しは約 23ms、図の描き直しは約 6ms
- 日時の属性は `?time=<属性名>`。省略時は、値の 8 割以上が ISO 8601（`2025-07-19`、`2025-07-19T12:00:00Z`、`+09:00` つきなど）として読める属性のうち、読める値が最も多いものを使う。無ければ「日時の属性がない」と出し、あった属性の名前を並べる
- 日付は `?tz=<IANA 名>` で区切る（`Intl.DateTimeFormat`）。省略時はブラウザの地方時。時差のない値（`2025-07-19 12:00` など）は、書いてある日付をそのまま使う。週は月曜はじまりで、両端の週はデータのある日だけ
- 区切りは日と週を切り替える（上下の段で共通）。4 週より長いデータでは週ごとを既定にした。日ごとの割合は意見の少ない日に大きく揺れて、帯が読めないため（このデータの 6 月は 1 日 26〜202 件）
- 上の段は全体の量。棒が意見の数、線が束ねる属性の値の数（同じ値の意見は 1 つに数える）。どちらも件数なので目盛りは 1 本
- 縦軸の左の余白は、一番長い目盛りの文字に合わせて決める。固定の 36px だった版では、幅 390px で「5,000」「2,500」「100%」の左端が図の外に 1.5px 出ていた（5 桁の件数ならもっと出る）。今は幅 390px で 42px、幅 1280px では 48px のまま
- 下の段は上位のまとまりの積み上げ（割合／件数）。20 色は色覚の違いで見分けられないので色に頼らない
  - 帯は灰色 2 つを交互に塗り、2px のすき間で分ける。青くするのは、触れた帯と、一覧で触れた・開いた行の帯だけ
  - 帯の上に表札を置く。3px おきに帯の上端・下端を測り、文字の幅の窓で「帯の高さの最小」が最も大きい所に置く。全文が入らなければ入るところまで切って「…」をつけ、4 文字も入らない帯には置かない
  - 値は吹き出しと「表で見る」（区切りごとの件数・割合の表）で読める
- 期間の選び方
  - ドラッグで選ぶ。日・週の区切りに揃う。今の期間の端の近くから始めると、その端を動かす
  - マウスで 1 回押すと、その日（週）だけを選ぶ
  - スマホは横になぞって選ぶ。`touch-action: pan-y` なので、縦になぞるとページがスクロールする。押すと値を見るだけで、期間は変わらない
  - 日付の入力欄でも選べる。印の名前を押すと、その印から次の印の前日までを選ぶ。期間は URL（`?from=&to=`）に残る
- 比べ方：選んだ期間とそれ以外で、まとまりごとの割合を比べる。差（ポイント）の大きい順に「割合が増えた」「割合が減った」を並べ、点で選んだ期間（塗り）とそれ以外（輪）を示す
  - 上位のまとまりは意見の数の割合で比べる（積み上げの図と同じ数え方）
  - 下位のまとまりは束ねる属性の値の数の割合で比べる。少数の投稿が同じ下位のまとまりに意見を並べて山を作るため（下記）
  - 期間の束ねる単位が 30 未満なら「割合の差は少数の投稿で決まる」と出す。期間に初めて意見が届いた下位のまとまりも数える
- 行を押すと、その期間のそのまとまりの意見を届いた順に出す（出典リンクつき、50 件から）。そのまとまりの区切りごとの件数を小さな棒で添え（選んだ期間の棒は青）、上位の表札と要約も出す
- 印：`?marks=2025-07-03:公示|Campaign+starts,2025-07-20:投票日|Election+day` で縦線を引く（`|` の後ろは英語のときの名前）。契約に置き場がないので URL 引数にした。カタログのリンクはこの印をつけ、期間は選ばずに開く。公示から投票日前日を選んだ状態で開くと、「それ以外」に 5 月が入り、抽出の入力の違い（下記「確かめた値」の最後）の混ざった比べが最初に出るため
- EN ボタンで、画面の文言と表札・要約・意見（`translations.en`）を英語に切り替える。`translations.en` が無ければボタンを隠す
- 割合が動いた理由（参加者の層が変わったのか、マニフェストや聞き手の側が変わったのか）は、このデータでは分けられない。ページにも「この比べ方では分けられない」と書き、理由は断定しない。このデータでは、5 月とそれ以降の比べに抽出の入力の違いも混ざる（下記「確かめた値」の最後）

### `public_result.json` に足りない項目（日時の属性）

- 日時そのものは `arguments[].attributes` に入る（自由形式なので契約の変更は要らない）。ここでは変換スクリプトが `created_at`（PR の作成日時、UTC の ISO 8601）を足した
- 足りないのは「どの属性が日時か」。このページは値から推定している。本体の公開ビューアも属性の型を値から推定している（kouchou-ai の `apps/public-viewer/components/report/attributeFilterUtils.ts` の `computeAttributeMetas`）が、型は数値とカテゴリの 2 つしかない。ISO 8601 の文字列はカテゴリになり、このデータの `created_at` なら絞り込みに 8,883 個の値が並ぶ
- 案 1：`computeAttributeMetas` に日時の型を足す。空でない値がすべて ISO 8601 として読めれば日時とし、絞り込みを期間で選べるようにする。契約は変えずに済む
- 案 2：属性の型と意味を宣言する場所を足す（下記「属性の型と役割」の `attribute_meta`。`created_at` に `"type": "datetime"` と何の日時かを書く）。値からは推定できない「何の日時か（投稿・作成・回答）」や「どの属性が同じ人の同じ投稿を束ねるか」も書ける。書いてあれば、このページの `?time=` と `?group=` の既定にできる
- 印（公示・投票日など）は表示の設定なので、入れるなら `public_result.json` ではなく可視化設定（`visualization_config.json`）の側
- 意見が抽出されなかった投稿は `arguments` に現れない。そのため日ごとの投稿の数は「意見のある投稿」でしか数えられない（7/19 は 521 本中 487 本）。下記「意見が抽出されなかった入力」

## 本体に入れるときに要るもの（複数の可視化に共通）

各節の「`public_result.json` に足りない項目」のうち、複数の可視化で同じものをここにまとめる。どれも試作を動かすためには要らない（今は URL 引数かスクリプトの引数で渡している）。本体に入れると決めたときに、その渡し方の代わりに要るものの控え。

### 属性の型と役割

意見ごとの値（日時・作者の種別・賛否スコア・孤立度など）は `arguments[].attributes` に入る。`attributes` は契約の対象外（自由形式）なので、値を足すだけなら契約の変更は要らない。無いのは、**その属性が何か**を宣言する場所。今は可視化ごとに、属性の名前を URL 引数（`?group=`・`?time=` など）かスクリプトの引数（`--group-by`）で渡すか、値の文字列の形から推している。本体の公開ビューアも型を値から推している（数値とカテゴリの 2 つ。上記「話題の流れの作り」）。

| 宣言したいこと | 要る可視化 | 今の渡し方 |
|---|---|---|
| どの属性が「同じ人の同じ投稿」を束ねるか | 自分の声を探す・要約から落ちた声・一緒に言われた話題・話題の流れ | `?group=` か `--group-by`（省略時は `comment_id`）。このデータの `comment_id` は「PR の中の課題 1 件」で、1 本の PR が複数に分かれるので、`pr_number` を渡した |
| どの属性が日時か、何の日時か（投稿・作成・回答） | 話題の流れ（`?time=`） | 値が ISO 8601 として読めるかで推す |
| 属性の型と、値の表示名（`idobata-policy-app[bot]` を何と出すか） | 要約から落ちた声（属性ごとの割合の棒） | 型は値の形から推し、値は生の文字列のまま出す |
| 何への賛否か | 賛否スライダー | 部分集合の `config.question` を対象に置き換えた |
| 事前計算した値が何を測ったか（k・束ねた属性・空間） | 要約から落ちた声（本体に入れて、孤立度を `attributes` に入れるとき） | 今は別の生成物（`?rare=`）に書いてある |

本体に入れるときの形の案：省略可能なトップレベルキー `attribute_meta` に、属性ごとの型・役割・表示名を置く。省略可能なキーの追加なので、schema_version は上げずに済む。このデータなら次のようになる。

```json
"attribute_meta": {
  "pr_number":   { "type": "id",       "role": "group" },
  "created_at":  { "type": "datetime", "label": "PR の作成日時" },
  "merged":      { "type": "boolean",  "label": "merge された" },
  "author_kind": { "type": "category", "label": "作者の種別",
                   "values": { "idobata-policy-app[bot]": "AI インタビュアー経由の市民の PR", "human": "人が直接出した PR" } }
}
```

- `role: "group"`：同じ人の同じ投稿を束ねる属性。書いてあれば、各ページの `?group=` とスクリプトの `--group-by` の既定にでき、ビューアが自分で束ね方を選べる
- `type: "datetime"`：話題の流れの `?time=` の既定にできる。何の日時か（投稿・作成・回答）は `label` に書く
- `values`：値の表示名。今は `idobata-policy-app[bot]` のような生の値を出しており、それが AI インタビュアー経由の市民の PR だという説明はこの README にしかない
- 賛否スコアの対象は `"stance_score": { "type": "number", "target": "原子力発電を今後も活用すること" }` のように書ける（上記「賛否スライダーの作り」。`config.opinion_stance_target` を足す案とどちらかにする）
- 事前計算した値を `attributes` に入れるとき（要約から落ちた声の孤立度 `rare_k10` など）は、何を測ったか（k・束ねた属性・空間）を書く
- 日時の型だけなら、契約を変えずに、本体の公開ビューアの型の推定（`computeAttributeMetas`）に足す道もある（上記「話題の流れの作り」の案 1）

### 意見が抽出されなかった入力

- 意見が 1 件も抽出されなかった入力は `arguments` に現れない。`comments` も元のコメントを公開したときだけ中身が入り（このデータでは空）、`comment_num` は数だけ（このデータの変換では意見のある入力しか数えておらず、18,802 は意見のある comment_id の数と同じ）。そのため、その入力の日時などの属性は契約のどこにも残らない
  - 話題の流れ：日ごとの投稿の数を「意見のある投稿」でしか数えられない（7/19 は 521 本中 487 本）
